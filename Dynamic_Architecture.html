Enterprise HRMS Architecture

Dynamic Employee Field Engine

A robust enterprise design separating the form into four layers: Sections > Fields > Options > Data.

employee_sections

Defines Major Profile Blocks

This table handles the major groupings. The most important column is storage_type, which tells the system if this section holds one object (single) or multiple objects (repeater).

Column Type Example
id PK 1
name String Personal Information / Education
storage_type Enum single / multiple

employee_fields

The Core Schema

This table is the heart of the engine. It dictates the label, grid width, input type, data source, and complex validations via JSON.

Basic Configurations

  • name: degree
  • label: Degree
  • field_type: text
  • component: input
  • column_width: 6

Validation JSON

{ "required": true, "numeric": true, "min": 0, "max": 5, "step": 0.01, "regex": "^[A-Za-z ]+$" }

Laravel loops this JSON to build dynamic Form Request rules.

UI Configuration JSON

{ "placeholder": "Enter Degree", "icon": "graduation-cap", "prefix": "", "suffix": "", "autofocus": false, "autocomplete": true }

Controls how the frontend renders the field.

File Upload Configuration

If field_type = file, extra configuration dictates the uploader behavior:

{ "accept": ["pdf", "jpg", "png"], "max_size": 2048, "multiple": false }

employee_field_options

Static Data Store

Only used when the field's `option_source` is set to `static` (for Select, Radio, Checkbox). This replaces massive JSON arrays with structured data.

field_id label value is_active
Gender Field Male male true
Gender Field Female female true
Blood Group Field O Positive O+ true

Option Source (Dynamic Dropdowns)

Relational Loading

Not every dropdown should store static options. Instead of saving thousands of options, add these columns to the `employee_fields` table:

  • option_source: static | table | api
  • source_table: departments | countries | designations
  • api_url: /api/v1/countries

Example Use Case:

  • Field: Department
  • Source: table
  • Table: departments
  • Label Column: name
  • Value Column: id

The frontend reads this configuration and dynamically queries the `departments` table via an API to load the dropdown choices.

Dynamic Approval Workflow Engine

A task-based routing engine that natively supports both Sequential and Random (Parallel) approval strategies.

Table 1: approval_workflows Configuration

Defines the workflow strategy for a specific module.

  • id (PK)
  • module_name "leave_request"
  • type Enum: 'sequential', 'random'
  • is_active true
Table 2: approval_workflow_steps Configuration

The blueprint of required approvers.

  • id (PK)
  • approval_workflow_id (FK)
  • step_order 1, 2, 3... (Used if sequential)
  • required_user_type Enum: Department, Division
Table 3: approval_requests Master Container

The overarching container linking the specific item to the workflow.

  • id (PK)
  • approvable_type "App\Models\LeaveRequest"
  • approvable_id 45
  • employee_id Crucial for OrganizationScoped
  • status pending, approved, rejected
Table 4: approval_step_requests Individual Tasks

The literal tasks assigned to approvers.

  • id (PK)
  • approval_request_id (FK -> Table 3)
  • workflow_step_id (FK -> Table 2)
  • status pending, approved, rejected
  • approved_by (FK: User who clicked Approve)

Strategy A: Random (Parallel)

Generates all tasks immediately. Any approver can approve at any time.

  1. Initiation: Employee submits request. The Master approval_requests record is created.
  2. Task Generation: The engine sees `type = random`. It immediately generates ALL approval_step_requests rows.
  3. Tasks Created Instantly:
    Task 1: Dept Head (Pending) Task 2: HR Admin (Pending)

    Both users receive notifications simultaneously.

Strategy B: Sequential

Generates tasks one by one. Step 2 does not exist until Step 1 is approved.

  1. Initiation: Employee submits request. Master record created.
  2. Task Generation: The engine sees `type = sequential`. It ONLY generates Step 1's task.
  3. Tasks Created Instantly:
    Task 1: Dept Head (Pending)

    The HR Admin sees nothing yet.

Engine Logic & Verification Checks

Why do we generate Task Rows?

By generating distinct approval_step_requests rows for each approver, we decouple the workflow state from the user. These rows act like "Inbox Items". It allows users to see exactly what is waiting on *them*, enables tracking exactly *who* approved *which* step, and natively supports parallel approvals where multiple users can approve their own specific task at the same time.

How it Checks: Random Workflows

When an approver clicks "Approve", the engine marks their specific Task row as approved. Then, the engine queries the database:

Are there any Tasks left where status = 'pending' for this Master Request?

If No, it means all approvers have completed their parallel tasks. The Engine updates the Master approval_requests to `approved`.

How it Checks: Sequential Workflows

When an approver clicks "Approve", the engine marks their Task as approved. Then, the engine queries the config:

Does a Step exist where step_order > current_step_order?

If Yes, it generates a new Task row for that next step. If No, it checks if any pending tasks exist. If not, the Master Request is finalized!

How OrganizationScoped Secures the Inbox

Because the individual approval_step_requests (the Tasks) belong to a Master approval_requests record, and that Master record holds the employee_id, the security is bulletproof.

When a user (e.g., a Department Head) loads their Inbox, the OrganizationScoped trait automatically appends a WHERE clause ensuring they only see Tasks where the originating employee_id belongs to their department. You do not need to write complex SQL to figure out who the manager is.
