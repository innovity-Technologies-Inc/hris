Approval Workflow Functional Breakdown

This document provides a complete, end-to-end breakdown of how the Innovity Approval Engine operates behind the scenes in the HRMS system, detailing the interactions between the package classes and the application's core logic.

The Core Database Models

The engine relies on a strict hierarchy of database tables to track state:

Workflow The Blueprint

vendor/innovity/laravel-approval-engine/src/Models/Workflow.php

Defines the overarching rules for a specific module (like "Promotion"). It tracks things like whether the flow is Sequential (one after another) or Random (anyone can approve in any order), and the required threshold of approvals.

  • Table: approval_workflows
  • Fields: id, name, module (e.g., 'promotion'), type (sequential/random), total_steps, required_approvals, is_active, created_at, updated_at

WorkflowStep The Blueprint Steps

vendor/innovity/laravel-approval-engine/src/Models/WorkflowStep.php

The individual tiers inside a Workflow (e.g., Step 1: Section, Step 2: Department, Step 3: Division).

  • Table: approval_workflow_steps
  • Fields: id, workflow_id (Foreign Key), name, step_order (1, 2, 3...), required_user_type (e.g., 'department'), created_at, updated_at

ApprovalRequest The Master Tracker

vendor/innovity/laravel-approval-engine/src/Models/ApprovalRequest.php

When a Promotion is created, one of these is generated. This is the master record that tracks the overall progress of that specific Promotion through the blueprint.

  • Table: approval_requests
  • Fields: id, workflow_id, approvable_type (e.g., 'App\Models\Payroll\Promotion'), approvable_id (e.g., 7), status ('pending', 'approved', 'rejected'), payload (JSON), created_at, updated_at

ApprovalStepRequest The Active Token

vendor/innovity/laravel-approval-engine/src/Models/ApprovalStepRequest.php

These are the individual "tasks" assigned to approvers. The engine generates these one by one (or all at once if random) to ask for a yes/no decision.

  • Table: approval_step_requests
  • Fields: id, approval_request_id (Foreign Key to master tracker), workflow_step_id (Foreign Key to blueprint step), approver_id (ID of user who took action), status ('pending', 'approved', 'rejected'), comments, action_taken_at, created_at, updated_at

Step-by-Step Functional Cycle

1

Initiation (Creating the Request)

The Hook

The core models (e.g., Promotion, Increment) use the Approvable trait. It is important to note that this trait does not automatically trigger the workflow when a model is saved. This is intentional to prevent accidental workflows starting when users save "Drafts" or when running database seeders.

The Ignition

To start the engine, you must manually call the helper method from your controller right after the model is created and ready for approval:

$promotion->startWorkflow('promotion');

When this generator is called, it performs the following:

  1. Looks up the Blueprint: Searches for an active Workflow record matching the module string.
  2. Creates the Master Tracker: Creates the polymorphic ApprovalRequest setting its status to pending.
  3. Hands off to the Dealer: Passes the new master request to the TaskEmitter.
  4. Broadcasts an Event: Dispatches the ApprovalRequested system event.
2

Task Emission

vendor/innovity/laravel-approval-engine/src/Services/TaskEmitter.php

The TaskEmitter's only job is to "deal the cards" (generate ApprovalStepRequests).

  • If Random: Creates a step request for every single step in the blueprint simultaneously.
  • If Sequential: Looks at the step orders (1, 2, 3), finds the next step that hasn't been created yet, and emits only that one step request.
3

Notification Routing & Approver Resolution

Catching the Step

In AppServiceProvider, there is an Eloquent event listener waiting for any ApprovalStepRequest to be created. Because it is attached to the database created event inside the Service Provider, the notification logic is entirely decoupled from your controllers.

Resolving Approvers

The engine generates a step requiring a specific authority level (e.g., "Department"), but it relies on your application's App\Services\ApproverResolver to find the right person.

  • The resolver looks at the employee and identifies who holds the required authority.
  • Note: This resolver bypasses standard global scopes to ensure routing succeeds regardless of who triggered the event.

Generating the Notifications

For every resolved approver found, the system loops through them and generates two types of notifications:

  1. Email Notification: Uses Laravel's standard Notification system to send an email via ApprovalActionRequiredNotification.
  2. Dashboard (In-App) Notification:
    • Dynamically builds the redirect URL by checking if a route named {module_name}.show exists.
    • Triggers NotificationServices::createNotification to generate the bell-icon alert with the URL attached.
4

User Interaction (The Frontend)

  • Viewing the Timeline: The targeted approver clicks the notification and is routed to the view page. The workflow_history.blade.php component reads the pending request.
  • Authorization Check: The blade file re-runs the ApproverResolver in real-time. If the logged-in user is authorized, the Approve/Reject buttons are rendered.
  • Submitting the Action: When the user clicks Approve/Reject, an Axios AJAX POST request is fired to the ApprovalActionController.
5

Package Processing (The Judge)

vendor/innovity/laravel-approval-engine/src/Services/ApprovalResolver.php

When Approved

  1. Updates specific ApprovalStepRequest to approved.
  2. Evaluates Master ApprovalRequest.
  3. Sequential: Asks TaskEmitter for next step.
  4. Random: Checks if required count is met.
  5. If complete, declares Master Request approved and fires ApprovalCompleted event.

When Rejected

  1. Updates specific ApprovalStepRequest to rejected.
  2. Sequential: Immediately kills the entire workflow, fires ApprovalRejected event.
  3. Random: Evaluates if threshold can still be reached, else fails immediately.
6

Finalizing the Core Data

Once the Innovity\ApprovalEngine finishes its mathematics, its job is strictly done. It broadcasts the final result back to the main Laravel application.

app/Listeners/WorkflowStatusListener.php

  • Intercepts the ApprovalCompleted or ApprovalRejected events.
  • Checks the workflow's module property (e.g., 'promotion', 'leave').
  • Fetches the core model and physically updates its status column in your database.

This clean separation ensures the package strictly handles the rules and timeline of the workflow, while the HRMS system handles the organizational security scoping, email notifications, and final model mutations!
